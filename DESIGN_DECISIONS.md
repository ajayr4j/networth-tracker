# Design Decisions

## Reasoning table

| Decision | Alternatives considered | Why this one |
|---|---|---|
| **JWT auth** (`djangorestframework-simplejwt`) over Django session auth | Session/cookie auth with CSRF tokens | Frontend and backend are separate apps on separate origins/ports (and will deploy to separate hosts — Netlify + Render). Stateless JWTs avoid cross-origin cookie/CSRF complexity and let the SPA hold the access token in memory and attach `Authorization: Bearer` headers explicitly. Trade-off accepted: tokens must be refreshed client-side and can't be server-side revoked before expiry — acceptable for a two-user personal-finance app with short-lived access tokens. |
| **Single unified `Holding` model** for both assets and liabilities (discriminated by `kind`) | Separate `Asset` and `Liability` models/tables | Assets and liabilities share every other field (category, label, owner, valuation history) and participate in the same net-worth sum (with a sign flip). One model means one CRUD API, one permission class, and one valuation-history mechanism instead of duplicating all three. `kind` as an enum is enough to distinguish them for the net-worth calc and UI grouping. |
| **Append-only `HoldingValuation`** rows, never updated/deleted | Store `current_value` directly on `Holding` and overwrite on edit | The spec requires historical snapshots to be immutable and a historical net-worth chart. An append-only valuation table makes "value as of date X" a simple query (latest row with `as_of <= X`) and makes the history free — no separate audit log needed. The cost is an extra join to find the "current" value, which is cheap at this data scale. |
| **Synchronous milestone detection** (checked inline when a valuation is recorded) | Async job / Celery task | Milestone crossings only need to be detected a few times a month at most (whenever someone updates a valuation), and the check is a cheap single query against 5 fixed `Milestone` rows. Adding a task queue (Celery/Redis) for this would be infrastructure the free-tier hosting target doesn't need and the spec doesn't require real-time/background processing elsewhere. |
| **TypeScript** on the frontend | Plain JavaScript | The API surface has many shaped objects (holdings, valuations, projections, timeline entries) flowing through multiple pages. Typing `src/api/*.ts` response shapes catches drift between backend serializers and frontend consumption at compile time rather than at runtime in production. |
| **Tailwind v4** for styling | CSS Modules, styled-components, a component library (MUI etc.) | A two-page-type app (dashboard-style data screens + forms) doesn't need a full component library's bundle size or theming system. Tailwind's utility classes keep styling co-located with markup and were fast to iterate with directly in JSX during development; v4's CSS-first config avoids a separate `tailwind.config.js` entirely. |
| **Workspace capped at 2 members** | Open-ended multi-member workspaces | The product is explicitly "a couple's" net worth tracker. Capping at 2 in `WorkspaceInvite` redemption keeps the ownership model (`individual` vs `joint`) unambiguous — with more than 2 members, "joint" would need to specify *which* members, which the spec doesn't ask for. |
| **`owner_type` + nullable `owner_user`** on `Holding` instead of a many-to-many "owners" relation | M2M `owners` field on `Holding` | Only two ownership shapes exist in the spec: one specific partner, or both jointly. A single nullable FK plus an enum expresses this exactly, and permission checks (`CanEditHolding`) stay a simple two-branch condition instead of an M2M membership check. |
| **404 (not 403) for cross-workspace access** | Always return 403 for any authenticated-but-unauthorized request | Returning 404 for a holding that exists but belongs to another workspace avoids confirming the resource's existence to someone who isn't a member of that workspace — a basic form of not leaking workspace membership/data existence to outsiders. 403 is reserved for the case where the requester *is* a workspace member but lacks ownership permission on a specific holding (where existence is already known). |
| **PostgreSQL via Docker Compose, with a `DATABASE_URL` escape hatch** | SQLite for local dev | The spec requires a relational DB and the production target is Postgres (Render). Developing against SQLite locally risks shipping Postgres-specific bugs (e.g. `DecimalField` precision, `JSONField` behavior) that only surface in production. Docker Compose makes local Postgres a one-command dependency instead of a manual install. |

## Future expansion ideas

- **Bank/market data integration** (explicitly out of scope for this submission) — auto-refresh stock/MF valuations via a market data API instead of manual entry, with the existing append-only `HoldingValuation` model requiring no schema change, just a new write path.
- **More than 2 workspace members** — would require `owner_type` to become a per-member assignment (or a join table) rather than a binary individual/joint enum, plus UI for showing who owns what among 3+ people.
- **Recurring reminders** for monthly check-ins (email or push notification when a month has no `MonthlyCheckIn` yet).
- **Soft currency/locale support** — amounts are currently INR-only (`formatINR` in the frontend); a `currency` field on `Holding` plus FX conversion would generalize this.
- **Exportable reports** (PDF/CSV) of net worth history and projections, reusing the existing `historical_series`/`forecast` service functions.
- **Audit log for settings changes** — `ProjectionSettings` updates currently overwrite in place; if accountability for *who changed the growth assumptions and when* becomes valuable, it could follow the same append-only pattern as `HoldingValuation`.
- **Revocable JWTs** — a token blacklist (simplejwt supports this as an optional app) if "log out all devices" or forced session invalidation becomes a requirement.
